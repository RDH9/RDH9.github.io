GPO Inheritance, Block Inheritance, and Enforced — Tested Hands-On

Group Policy inheritance is one of those Active Directory topics that sounds simple on paper but doesn't fully click until you actually break it in a lab. Here's what I found testing it hands-on.

The inheritance order

GPOs apply in this order: Local → Site → Domain → OU (with nested OUs applying parent-to-child). Settings merge by default, and if two GPOs conflict on the same setting, the one closest to the object wins.

Testing Block Inheritance

I created a domain-wide GPO with a login banner, linked at the domain root. Using PowerShell:

New-GPO -Name "Domain-Banner-Policy" | New-GPLink -Target $domain
Set-GPRegistryValue -Name "Domain-Banner-Policy" `
  -Key "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System" `
  -ValueName "legalnoticetext" -Type String -Value "Monitored system"

Then I enabled Block Inheritance on a test OU:

Set-GPInheritance -Target "OU=Finance,DC=rdhwin,DC=lab" -IsBlocked Yes

As expected, the banner GPO stopped applying to that OU.

The trap: Enforced beats Block Inheritance

This is the classic gotcha. I set the domain-level GPO to Enforced, and it started applying to the Finance OU again — despite Block Inheritance still being active there.

The rule to remember: Enforced always overrides Block Inheritance. It's an easy thing to get backwards the first time, but it makes sense once you think of Enforced as "this policy is non-negotiable, no matter what's downstream."

Delegation of Control ≠ GPOs

One thing I mixed up early on: GPOs configure settings pushed to users/computers. They don't grant permissions to people. If you want a helpdesk group to reset passwords for one OU only, that's Delegation of Control — a completely separate AD mechanism that modifies the ACL on the OU itself, not a policy push.
